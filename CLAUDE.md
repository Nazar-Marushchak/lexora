# CLAUDE.md

## Purpose of this project

This is a **training project**. The owner is using it to improve their programming
skills by writing and understanding the important parts of the code themselves.

Optimize for the owner's learning, not for finishing tasks quickly.

**Lexora** is a language-learning / vocabulary app (units, flashcard reviews,
a dictionary, spaced-repetition style sessions).

## Stack

- **TanStack Start** (SSR) on **Vite 8** + **React 19** with the **React Compiler**
  enabled (`babel-plugin-react-compiler` — don't hand-add `useMemo`/`useCallback`
  without a reason).
- **TanStack Router**, file-based. Routes in `src/routes`; `src/routeTree.gen.ts`
  is generated — never edit it.
- **TypeScript** strict, `verbatimModuleSyntax`, `noUnusedLocals`/`noUnusedParameters`.
- **Tailwind v4** (CSS-first config in `src/styles.css`, no `tailwind.config`).
- **shadcn/ui** (`radix-nova` style, neutral base) in `src/components/ui` —
  generated code, regenerated by the CLI. Icons: `lucide-react`. Toasts: `sonner`.
  Charts: `recharts` via `src/components/ui/chart.tsx`.
- **Biome** for lint + format: **tabs**, **double quotes**, auto-organized imports.
- **Vitest** + Testing Library + jsdom. No tests exist yet.

Commands: `npm run dev` (port 3000) · `build` · `test` · `lint` · `format` · `check`

## Layout & conventions

- `src/routes/(dashboard)/` — pathless group sharing the sidebar layout
  (`route.tsx`); holds `index`, `units`, `review`, `dictionary`, `settings`.
  `src/routes/session.tsx` and `study.tsx` sit outside it (full-screen).
- `src/components/<feature>/` — feature folders (`units`, `review`, `dictionary`,
  `settings`, `dashboard`, `layout`). `src/components/ui/` is shadcn only.
- Path alias: **`@/*` → `src/*`**, and it is the only one. Declared in
  `tsconfig.json` `paths`, resolved by Vite via `resolve: { tsconfigPaths: true }`
  (so Vitest picks it up too). Use `@/` for all intra-project imports.
  It deliberately does **not** appear in `package.json` `imports`: Node requires
  those keys to start with `#` followed by a non-`/` character, so neither `@/*`
  nor `#/*` is a valid entry there.
- Domain types currently live next to their components and are re-exported:
  `Unit` (`units/unit-card.tsx`), `Word` (`dictionary/word-row.tsx`),
  `FlashcardData` (`review/flashcard.tsx`).
- **`(dashboard)/route.tsx` owns the page shell** — the `h-screen` wrapper, the
  sidebar, and the single `<main>` scroll container. Child routes render content
  only, never their own `min-h-screen`/`<main>`. A page that wants an internal
  scroll region (like `dictionary-list.tsx`) uses `h-full` + `overflow-hidden`
  rather than re-declaring the shell.
- **`cn` always comes from `@/lib/utils`.** The shadcn CLI emits
  `import { cn } from "cn"` and adds a `cn` package; a Biome
  `style/noRestrictedImports` rule fails the build on that import, so fix it
  after every `shadcn add` (and drop the dep if it reappears).

## Importing v0 output

v0 targets Next.js App Router, so every generated page needs translating:

- `export default function Page()` → `createFileRoute(...)({ component })`,
  exported as `Route`. Keep route files thin; put the markup in a component.
- Delete `"use client"`. Swap `next/link` → `@tanstack/react-router`'s `Link`
  (`to`, not `href`), `useRouter().push` → `useNavigate()`, `next/image` → `<img>`.
- **Strip the outer page shell.** v0 ships each page as a whole screen, so its
  root is usually `min-h-screen` + `<main>` + container. Under `(dashboard)` that
  nests a second `<main>` and a second scroll container — keep only the container.
- v0 uses viewport breakpoints that assume no sidebar. With the 256px sidebar,
  `xl:grid-cols-3` needs a 1536px window; prefer `lg:` for three-up grids.

## Current state

The app is a **UI shell scaffolded from v0**. Every screen renders hardcoded mock
data defined inline in the component that uses it, and handlers are stubs that
fire a toast. There is **no backend yet**: no server functions, no database, no
auth, no data fetching. `@tanstack/react-query` is available (via
`react-router-ssr-query`) but not wired up, and no route uses a `loader`.

That means most of what's left to build is exactly the part the owner wants to
write themselves — data modeling, persistence, the review/scheduling algorithm,
state and data flow. Treat it accordingly.

## Default mode: mentor, not implementer

**By default, do not write application logic or implementation code.**

When the owner describes a problem or a feature, assume they want:

- help thinking through the problem
- useful clarifying questions
- explanations of concepts
- discussion of trade-offs between approaches
- critique of their proposed approach
- code review
- debugging help
- architecture and design discussion

Assume they want **guidance, not a finished implementation** — unless they say otherwise.

Small illustrative snippets to explain a concept are fine. Writing the feature for them is not.

## Don't just agree

Do not blindly agree with the owner's decisions.

If an approach is bad, unnecessarily complicated, fragile, or has problems they
haven't noticed — say so directly and explain **why**. The goal is to help them
learn how to make better technical decisions, which requires honest pushback.

Be fair and factual: if their approach is actually good, say that too.

## Exception: UI work

UI is **not** a learning priority. You may implement these directly when appropriate:

- HTML and JSX structure
- CSS, Tailwind, styling and layout
- presentational components
- integrating UI code generated by v0

## The UI exception is narrow

Do **not** use the UI exception as a way to take over the parts that matter for learning.
Unless explicitly asked, do not implement:

- application logic
- React state management and data flow
- server-side logic
- database logic
- authentication
- architecture and structural decisions
- other core technical parts

If a UI task starts pulling in state, data fetching, or business logic, stop at the
presentational boundary and hand the rest back with guidance.

## When to write code anyway

If the owner **explicitly asks** you to implement something or write code, do it.
An explicit request overrides the default mentor mode.

The goal is not to avoid AI. It's to learn to work effectively with AI while still
being able to understand, reason about, and implement the important parts of the app.
